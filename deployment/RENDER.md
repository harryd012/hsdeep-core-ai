# Going live on Render

`render.yaml` (repository root) is a Render Blueprint: applying it creates the
API, worker and web services plus managed PostgreSQL and Redis (Key Value) from
this repository. This page is the go-live checklist.

## What the Blueprint creates

| Render resource | Role | Notes |
|---|---|---|
| `hsdeep-api` (web) | `RUNTIME_MODE=api` | Runs `alembic upgrade head` as the pre-deploy command; health check `/health/ready`. |
| `hsdeep-worker` (background worker) | `RUNTIME_MODE=worker` | Scheduler ticks and RCA/EventBus consumers. Keep it at one instance. |
| `hsdeep-web` (web) | Next.js standalone | `NEXT_PUBLIC_API_URL` is compiled in at build time. |
| `hsdeep-db` (PostgreSQL 16) | Primary database | Private network only. |
| `hsdeep-redis` (Key Value) | Redis | Private network only, `noeviction`. |

Starting cost on the plans in the file is roughly US$60-120 per month; change
`plan:` values to scale.

## You do (accounts and secrets are never handled by automation)

1. Push the branch you want to deploy to GitHub (see "Code on GitHub" below).
2. In Render: **New > Blueprint**, connect the GitHub repository, pick the branch.
   Render reads `render.yaml` and lists the resources.
3. Fill in the values it prompts for (`sync: false`):
   - `CORS_ORIGINS`: the web origin, e.g. `https://app.example.com`
   - `NEXT_PUBLIC_API_URL`: the API origin, e.g. `https://api.example.com`
   - `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`: optional. Empty keeps
     billing checkout and the Stripe webhook off (they answer 501). The
     webhook endpoint to register in Stripe is
     `https://api.<domain>/api/billing/webhook`.
   - `APP_PUBLIC_URL`: the web origin, used to build links in emails.
   - Email (optional for the pilot): `EMAIL_TRANSPORT` starts as `none`, so
     password reset and invitations answer 503. To turn email on, set
     `EMAIL_TRANSPORT=smtp` and fill `SMTP_HOST`, `SMTP_USERNAME`,
     `SMTP_PASSWORD`, `EMAIL_FROM` (any SMTP provider: SES, Postmark,
     SendGrid, Mailgun, SMTP2GO). Mail is queued by the API and sent by
     `hsdeep-worker` every 30 s; failures retry with backoff (5 attempts).
   `PUBLIC_SIGNUP_ENABLED` is `false` (invite-only pilot): every tenant is
   created with the step 7 bootstrap. With email on, self-service sign-ups
   must confirm their email before their next sign-in; turn sign-up on only
   with email configured and abuse protection (CAPTCHA) in place.
   `JWT_SECRET_KEY` and `SECRET_ENCRYPTION_KEY` are generated by Render. Do not
   regenerate `SECRET_ENCRYPTION_KEY` later: stored collector credentials are
   encrypted with it.
4. Apply. The first API deploy runs the migrations.
5. Custom domains: add `api.<domain>` to `hsdeep-api` and `app.<domain>` to
   `hsdeep-web`, create the DNS records Render shows, wait for TLS.
6. If the domains differ from step 3, update `CORS_ORIGINS` / `NEXT_PUBLIC_API_URL`
   and redeploy `hsdeep-web` (the API URL is a build-time value).
7. Bootstrap the empty database once, from the `hsdeep-api` **Shell** tab.
   This syncs the plan catalog (public signup fails until plans exist),
   creates your operator tenant with an active subscription, and creates its
   Owner login. Type the password yourself; it is hashed and never logged.
   ```bash
   SEED_TENANT_ID=$(python -c "import uuid; print(uuid.uuid4())") \
   SEED_TENANT_NAME="Your MSP" SEED_PLAN_TIER=enterprise \
   SEED_ADMIN_EMAIL=you@example.com SEED_ADMIN_PASSWORD='choose-a-strong-one' \
   python scripts/seed_admin.py
   ```
   Re-running it is safe: existing tenants, users and subscriptions are left alone.

`autoDeploy` is off: deploys happen when you trigger them, so a push to the
branch never ships by itself.

## Code on GitHub

Render builds from GitHub, so the deployed app is whatever the chosen branch
holds there. The local branches form one linear stack:

```
main < feat/ecc1-command-center < feat/ui-page-kit < feat/topology-meraki
     < feat/topology-l3 < chore/deploy-readiness
```

plus `fix/api-quota-api-key-only` (one commit on `main`). To deploy everything:
fast-forward `main` to `chore/deploy-readiness`, merge
`fix/api-quota-api-key-only`, run the suites, push `main`, and point the
Blueprint at `main`. Work that exists only as uncommitted files in a checkout
is not deployed.

Accounts lock for `LOGIN_LOCKOUT_MINUTES` (default 15) after
`LOGIN_MAX_FAILED_ATTEMPTS` (default 5) consecutive wrong passwords. A
locked user sees the generic sign-in error; an admin password reset
(`POST /api/auth/users/{id}/password`) unlocks the account.

## Verify after deploy

- `https://api.<domain>/health/ready` returns 200 (PostgreSQL and Redis reachable).
- `https://app.<domain>/` loads and `/login` signs in.
- The API logs show `Runtime mode : api (scheduler=False ...)`; the worker logs
  show `scheduler=True`.
- Startup did not fail the production checks (`APP_ENV=production` refuses
  placeholder secrets, wildcard CORS, `DEBUG=true` or `FORCE_HTTPS=false`).

## Operations

- **Backups**: Render takes daily PostgreSQL backups; paid plans add
  point-in-time recovery. Run one restore drill into a scratch database before
  onboarding customers (`deployment/BACKUP_RESTORE.md`).
- **Logs**: `LOG_FORMAT=json`; add a Render log stream to your log platform.
- **Uptime**: point an external monitor at `/health/ready` and `/`.
- **Metrics**: `/metrics` (Prometheus) needs `Authorization: Bearer
  $METRICS_BEARER_TOKEN` (generated by Render, readable in the env group).
  Without a token configured it answers 404 in production.
- **Rollback**: Render keeps previous deploys; roll back the service, and only
  downgrade a migration if the release notes say it is safe.

## Known gaps before paying customers

- **Collectors on customer sites.** A cloud-hosted backend cannot reach private
  SNMP/SSH/WinRM addresses. Customer-site polling needs the edge agent, which is
  in progress and not yet in this repository.
- **AI features** call Ollama (`OLLAMA_HOST`). Render has no GPUs; point it at
  a separately hosted model or those features stay degraded.
- **Cross-process events.** The EventBus is in-process; RCA for incidents
  created through the API (not by monitoring) needs a shared transport
  (`deployment/README.md`, "Known Phase 9B prerequisites").
- **Build-arg passing** of `NEXT_PUBLIC_*` env vars into the Docker build is
  Render's documented behaviour. STATUS = Needs Verification on the first deploy:
  open the site and confirm API calls go to `NEXT_PUBLIC_API_URL`, not localhost.
