# P1.1 — Command Center Brief Latency Fix

**Status: Done. No commit made. No frontend timeout changed. P2 not started.**

## 1. Goal
Get `command_center_brief()` to complete **well inside the existing 10-second frontend
timeout** (target `<5s` preferred, `<10s` required), without:
- changing the frontend timeout,
- changing P1 semantics or KPIs,
- starting P2 (no rollup table, no redesign).

## 2. Root cause
`command_center_brief()` runs **5 incident aggregate queries**, each issuing a `SELECT COUNT(*)`
over the `incidents` table. With **5 partial indexes** already present that carried
`WHERE (is_deleted = false)`, PostgreSQL could **not** prove that predicate implied the ORM's
actual query expression — `Incident.is_deleted.is_(False)`, which appears **244 times** across
the codebase. Result: every aggregate ran a **Parallel Sequential Scan** over the ~4.8 GB
`incidents` heap.

In other words: the indexes existed but were **invisible to the planner** because
`is_deleted = false` ≠ the planner's ability to use `WHERE (is_deleted IS false)`.

## 3. Fix (indexes added, no rollup, no new tables)
All 4 partial indexes lead with `tenant_id` (which stays a real SQL predicate) and use
`IS false` to match the ORM's emitted predicate:

| Index | Columns | Type |
|---|---|---|
| `ix_incidents_tenant_opened_active` | `(tenant_id, opened_at)` | partial `WHERE is_deleted IS false` |
| `ix_incidents_tenant_resolved_active` | `(tenant_id, resolved_at)` | partial `WHERE is_deleted IS false` |
| `ix_incidents_tenant_status_severity_active` | `(tenant_id, status, severity)` | partial `WHERE is_deleted IS false` |
| `ix_incidents_tenant_last_alert_active` | `(tenant_id, last_alert_at DESC)` | partial `WHERE is_deleted IS false` |

Also introduced (P1.1 scope, no P2):
- `IncidentRepository.active_counts()` — returns `open_incidents` and
  `critical_open_incidents` (via `count(*) FILTER (WHERE severity='critical')`) in a **single**
  indexed scan instead of 2 separate queries.
- `OperationalIntelligenceService.command_center_brief()` now calls `active_counts()`.

## 4. Why `IS false` and not `= false`
`is_deleted` is `NOT NULL`, so `IS false` ≡ `= false` logically. But PostgreSQL only lets a
partial index with `WHERE (is_deleted = false)` be used when the query predicate the planner
can prove is itself `IS false`. Using `IS false` is the only form that lets the planner actually
use these indexes.
